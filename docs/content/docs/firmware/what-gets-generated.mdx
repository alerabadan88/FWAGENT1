title: What gets generated
description: Thirteen files, and what each is for.
---

```
config.h      pin macros, clock, baud, watchdog period, firmware identity
sensor.h      the shared status type
main.c        init, read loop, UART reporting
uart.c/.h     blocking transmit, integer formatting
watchdog.c/.h recovery, with the post-reset trap handled
<sensor>.c/.h one pair per sensor
```

## The reporting loop

Readings go out over USART at the configured rate:

```
ATmega328P 0.1.0 (765e0d32) up
DHT22 T=26.9C RH=65.8%
HC-SR04 d=1245mm
LDR adc=512 (2502mV)
DHT22 ERR=2
```

A failed read prints an explicit status code. **No placeholder value is ever
emitted in place of a measurement**, so an unwritten driver or a dead sensor
cannot be mistaken for data.

Formatting is a hand-rolled integer routine rather than `printf`, which would
cost more flash than the whole rest of the image.

## It adapts to the part

The USART index is read from the part, so the same template renders `UDR0` on
an ATmega328P, `UDR1` on an ATmega32U4, and unnumbered `UDR` on an ATtiny2313.
A part with no USART is refused with its reason.

## Identity

`FIRMWARE_VERSION` and a `BUILD_ID` derived from the configuration are printed
at boot, so a unit on a bench maps back to the build that produced it. Same
inputs give the same id; change a pin and it changes.

## Determinism

Generation is deterministic. The same input produces byte-identical sources,
which is what makes the SBOM digests worth anything.
