---
title: Schematic netlist
description: The strongest input, because it carries the wiring.
---

A KiCad `.net` export already names the MCU pin on each connection:

```
(net (code "3") (name "/DHT_DATA")
  (node (ref "U1") (pin "4") (pinfunction "PD2") (pintype "bidirectional"))
  (node (ref "U2") (pin "2") (pinfunction "DATA") (pintype "bidirectional")))
```

So the pin arrives MCU-native and nothing about the wiring is asked or assumed.

```bash
fw-agent schematic board.net --build
```

## What is settled by evidence

**Which component is the MCU** is decided by asking the toolchain whether a
value names a part it can target. `U1` being first is not evidence;
`ATmega328P-PU` resolving to `atmega328p` is. No targetable part, or more than
one, is refused rather than picked between.

**Which pin a sensor sits on** comes from the net joining it to the MCU.

## What it filters

- **Power rails**, by name and by every node on them being a power pin — so a
  shared ground does not read as every part being wired to every other.
- **Passives.** A pull-up sharing the data line is not mistaken for a sensor.

## What it reports rather than invents

- Parts with no driver, named, with the pins they are on.
- Connections whose MCU pin the schematic does not name.
- That **a netlist carries no crystal frequency and no supply voltage**. Those
  are shown as defaults that must be confirmed, not as settled facts.

## Limits

Only KiCad's S-expression export is parsed. Altium is not supported.
